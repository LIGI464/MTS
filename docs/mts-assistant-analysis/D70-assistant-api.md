# D70 · API диалога «Помощник МТС»

Продолжи работу в `LIGI464/MTS` от принятого SHA реализации D10–D40. Рабочая ветка содержит результат D60. Материалы комплекта доступны в ветке документации. Сверяй точки входа с принятым состоянием приложения. [Старт](D50-start.md) · [Поиск](D60-similar-incidents.md) · [Интерфейс](D80-assistant-ui.md)

Задание этого блока — один серверный сценарий диалога для двух входов в «Помощник МТС». В деталях кнопка «ИИ-анализ» расположена наверху рядом с SLA и передаёт уже открытый инцидент. С пульта тот же чат открывается закреплённой кнопкой «Помощник МТС» и может начать разговор без выбранной заявки. [Визуальная спецификация](DESIGN.md)

## Точки входа в репозитории

| HTTP и конфигурация | `apps/api/src/analysis/index.ts`, `apps/api/src/http/index.ts`, `apps/api/src/http/config.ts`, `apps/api/src/http/operator-token.ts` |

Существующий `POST /api/v1/incidents/:id/analysis` формирует короткий анализ по `AnalysisResultSchema`. Сохрани совместимость этого маршрута. Новый диалог использует те же серверные правила провайдера и обработки ошибок, а похожие случаи получает от D60.

## Вход и продолжение диалога

1. Добавь `POST /api/v1/assistant/chat`. Определи в `@mts/contracts` строгие схемы запроса и ответа и используй их в серверном обработчике и веб-клиенте. Для запроса определи режим `incident` или `dashboard`, ограниченный текст вопроса и проверяемый контекст заявки. Ограничь размер вопроса, служебных полей и истории, которую принимает сервер. Ответ проверяй перед выдачей и на клиенте.
2. В режиме `incident` используй ID открытой карточки. Разреши первый запрос без пользовательского вопроса. Возьми факты об инциденте из текущего снимка и/или записи, возвращаемой `runtime.getTicket(id)`. Проверь наличие ID и, где доступно, актуальную версию. После открытия «ИИ-анализ» интерфейс сразу запрашивает анализ конкретной карточки. Шаг запроса номера в этом режиме не нужен.
3. Режим `dashboard` начинается с короткого приглашения «Укажите ID инцидента или опишите симптомы». Запрос без полезного контекста возвращает `needs_context` без вызова провайдера. Если пользователь указал ID, проверь его по репозиторию данных, поддержи текущий и архивный инцидент. При неизвестном ID верни понятное уточнение. При осмысленном описании без ID передай ограниченный набор признаков в D60 и ищи по симптомам. Если признаков недостаточно, задай один конкретный вопрос, например «Что именно не работает и в каком сервисе?»
4. Уточняющий вопрос использует подтверждённый контекст открытого диалога. Для известной заявки перечитывай её из серверных данных. Для поиска без ID сохраняй ограниченный контекст описания симптомов. При явном переходе к другому ID или новой теме обновляй контекст. Ответы от старой заявки или предыдущей версии не должны попадать в новую карточку чата. Веб-клиент возвращает запросу контекст, который можно проверить, и отменяет или игнорирует устаревший ответ. Подготовь интерфейс транспорта для такого поведения.
5. Предусмотри короткие ошибки в принятом формате API для неверного запроса, несуществующего инцидента при запуске из карточки и недоступных данных. `needs_context` и «Подходящих завершённых инцидентов не найдено» — нормальные результаты диалога. Обработай их как состояния ответа. Помощник читает записи и предлагает проверяемые следующие шаги. Из диалога не выполняются смена координатора, закрытие, запись решения и другие мутации.

## Ответ, похожие случаи и ссылки

- При получении контекста вызывай локальный сервис D60. Его источник — текущие записи и архив SQLite. Используй найденные записи с последним состоянием `Resolved` или `Closed`, включая архивные `present=false`, если они подошли по признакам. Исключение текущей заявки, ранжирование и лимит выдачи определяет D60.
- У успешного ответа явно различай короткую выжимку, следующие шаги, список похожих завершённых случаев и режим формирования `llm` или `rules`. У каждого случая передай ID, заголовок, статус, дату завершения при наличии, проверенную ссылку ITSM и подтверждённые фрагменты. Показывай «Симптом», «Что сделали» и «Результат» по полям описания и решения из записи. Если решение содержит одно неделимое описание, покажи его целиком под «Решение». Сам статус «Завершён» не подтверждает восстановление конкретной функции.
- Строй ссылки на стороне приложения из полученных записей. Используй доступный разрешённый внешний URL ITSM или настроенный шаблон `MTS_ITSM_URL_TEMPLATE` по действующей нормализации. Для архивного случая без внешнего адреса указывай `/itsm/incidents/${encodeURIComponent(id)}` по правилу `ticketPath`. Правило `itsmHref` допускает внешний HTTPS-адрес без встроенных учётных данных. Не подставляй адрес продукта. ID и URL задаёт сервер или доверенный код приложения.
- Модель получает только выбранные факты текущей записи, ограниченный вопрос и доказательства по найденным случаям. Для ссылок на случаи она может указать только ID из переданного списка. Названия, статусы, даты, идентификаторы и URL собираются по данным приложения. Если модель предлагает отсутствующий ID либо выдаёт неподходящий формат, отдай локальный ответ по тем же данным.
- Отвечай от лица «Помощника МТС» по-русски, в деловом стиле и короткими абзацами или пунктами. Разделяй «Из карточки» и «Что проверить», чтобы совет читался отдельно от подтверждённого факта. Подтверждённая замена детали относится к выполненным действиям. Предложение проверить ход относится к следующим шагам. Когда похожих случаев нет, сообщи об этом и при необходимости попроси один признак, который поможет уточнить поиск.

## Провайдер и локальный режим

1. Переиспользуй серверный клиент codex.sale из `packages/analysis/src/provider/index.ts`. Используй текущие `MTS_AI_MODE`, `MTS_OPERATOR_TOKEN`, `CODEX_SALE_API_KEY`, `CODEX_SALE_MODEL`, `CODEX_SALE_BASE_URL` и `MTS_AI_TIMEOUT_MS`. Ключ провайдера остаётся серверным. Правила `liveAnalysisEnabled` и проверки bearer применяются к новому маршруту, как в действующем анализе. Учитывай существующие пределы параллельности и частоты для платных запусков и не создавай обход через второй маршрут.
2. Построй работоспособный локальный ответ на сервере до вызова модели. Поиск D60 выполняется и в режиме `rules`, и в режиме `llm`. При отсутствии настроек, тайм-ауте, ошибке провайдера или невалидной структуре отдай локальную выжимку, проверенные ссылки и причину резервного режима. Обычная проверка в облаке проходит без ключей и внешнего запроса.
3. Передавай модели только необходимые очищенные и ограниченные поля. Текст заявки, прошлых решений и вопрос пользователя передавай как данные. Сохрани существующие требования к валидации, тайм-аутам и `Cache-Control: no-store`. Если переиспользуешь внутреннее кэширование, учитывай режим, ID/версию, вопрос, контекст и версии доказательств. Обновление импорта и смена версии должны давать актуальные сведения. `demo.reset` сбрасывает устаревшие результаты.
4. Для автономного `npm run dev:web` подключи совместимый ответ на репозиторных фикстурах через существующий mock-механизм. Проверяй полноценный серверный маршрут отдельно на тестовой копии ITSM JSON.

## Проверки и передача в блок интерфейса

Расширь существующие проверки `apps/api/tests/analysis.test.ts` и `packages/analysis/tests/` там, где изменилось поведение. Прогони `npm run check`, `npm test` и `npm run build`. Провайдер тестируй подстановкой ответа и ошибки по схеме действующих тестов.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Первый запрос из открытых деталей | Выжимка и найденные случаи для переданного ID, без вопроса об ID |
| Открытие с пульта без контекста | Один вопрос про ID или симптомы, вызова провайдера нет |
| С пульта передали действительный ID | Открывается диалог с контекстом конкретной заявки |
| С пульта передали достаточное описание без ID | D60 ищет по признакам, ответ указывает проверенные завершённые случаи |
| Явный ID не найден, или по валидному запросу нет совпадений | Соответствующее уточнение или пустая подборка, без неподтверждённых карточек |
| Два вопроса по одной заявке, затем переход к другой | Сначала сохраняется контекст текущей заявки, после переключения данные изолированы |
| Подошла запись `present=false` | В ответе есть актуальный ID завершённого случая и открываемая карточка архива |
| Провайдер вернул несуществующий ID, невалидный ответ или тайм-аут | Рабочий локальный ответ по D60 |
| Повтор запроса после обновления записи или сброса демо | Факты и результаты актуальны |
| Запрос сменить координатора или закрыть заявку | Состояние заявки и архив не изменились |

Передай исполнителю интерфейса фактические имена экспортированных схем, путь маршрута, формат запуска для двух режимов, пример ответа с двумя случаями, пример `needs_context` и способ определить `rules` для подписи в чате. Сдай SHA принятой базы, изменённые файлы, команды и результаты проверок.
