# D60 · Поиск похожих завершённых инцидентов

**Промт для облачного GPT.** Реализуй локальный поиск по архиву ITSM в `LIGI464/MTS` для чата «Помощник МТС». Выполняй блок на рабочей ветке новой фазы от принятого SHA D40 из `docs/mts-dashboard-review`. D10–D40 ещё в работе на момент подготовки задания. Сверь полученный SHA и результат приёмки перед разработкой. Прочитай README и спецификацию текущего пакета, затем проверь названные ниже файлы в принятой ветке. Для реализации и тестов используй содержимое репозитория и синтетическую SQLite.

D60 отвечает за поиск и факты из архива. D70 подключит поиск к серверному API диалога и составлению ответа. На выходе D60 нужны реальные записи, из которых можно показать краткую выжимку, статус и ссылку на карточку в реестре.

## Источник и выбор записей

1. Проследи `prepareItsmArchive` в `apps/api/src/store/itsm.ts`, его подключение в `apps/api/src/store/index.ts` и `apps/api/src/source/index.ts`, тип `DashboardRuntime` в `apps/api/src/runtime-contract.ts`, контракт карточки в `packages/contracts/src/incident-workflow.ts` и GET в `apps/api/src/itsm/index.ts`. В `dashboard.sqlite` `itsm_incidents.latest_seq` указывает на последнюю версию в `itsm_history`. `TicketSummary` содержит ID, версию, канонический `state`, `resolvedAt`, продукт, сервис и `present`. Описание и решение хранятся в исходных полях сохранённой записи. Для краткого симптома используй `shortDescription` или `description` из той же версии.
2. Добавь минимальную выборку только для чтения через существующий слой архива и runtime. Она должна получать необходимые поля из актуальных архивных версий без отдельного запроса карточки с полной историей на каждого кандидата. Учитывай записи с `present: false`, доступные через обычный GET карточки. Проверяй архивное состояние при запросе. Изменение только текста решения и повторное открытие заявки должны отражаться в следующем поиске, в том числе после рестарта. Выборка не записывает данные и не меняет порядок существующей истории.
3. Кандидат считается завершённым при каноническом `state` **`Resolved` или `Closed`** в последней версии. `Research`, активные и прочие состояния исключаются, даже если исходная строка содержит `completionDate` и `solution`. Повторно открытая заявка исключается, даже если раньше была закрыта. Запись, исчезнувшая из текущего файла после завершения, допустима. Оставь один результат на каждый строковый ID. Исключи ID открытой карточки из аналогов при поиске из деталей.
4. Сохрани существующий `POST /api/v1/incidents/:id/analysis` и его сценарий оценки рисков и рекомендации команды. В текущей основе он получает кандидатов из `snapshot.incidents`, а `packages/analysis/src/rules.ts` учитывает `Research` для рекомендации команды. У поиска завершённых заявок свой набор кандидатов из SQLite. Рабочий JSON `MTS_DATA_DIR/character_problems.json`, текущий снимок пульта и последние 50 событий сами по себе архивом для D60 не служат.

## Поведение поиска

- Поддержи поиск по открытому инциденту и поиск по осмысленному описанию симптомов из чата без выбранной карточки. При известном ID контекст бери из реальной заявки. Дополнительные слова оператора помогают уточнить сходство. Общая просьба «Найди похожие завершённые инциденты» на карточке использует данные карточки. Неизвестный явный ID возвращает отдельный результат для D70. Если ID не задан и симптомов нет, верни результат «нужен контекст», чтобы чат мог уточнить ID или симптомы.
- При ранжировании используй нормализованные продукт и сервис, заголовок, краткое и полное описание. Сопоставляй кириллицу без зависимости от регистра, лишней пунктуации и `ё/е`. Учитывай содержательные совпадения симптомов и уточнение оператора. Пустые поля и общие слова вроде «инцидент» не являются признаками сходства. Совпадение продукта и сервиса усиливает результат, а одного названия продукта или даты недостаточно. Документируй в тестах правило достаточного совпадения, включая поиск только по симптомам.
- Верни до пяти подтверждённых аналогов. Сначала сортируй по релевантности, при равенстве используй дату завершения по убыванию, затем строковый ID для стабильного порядка. Отсутствующая дата не является датой завершения и располагается после известных при равном ранге. Осмысленный запрос без убедительных совпадений возвращает пустой результат. Ограничь размер входных подсказок и текстов, возвращаемых из архива. Предел выдачи применяется к ранжированным совпадениям, чтобы более старый релевантный инцидент не пропал из-за предварительного ограничения по дате.
- Собери типизированный результат для D70 с вариантами «найдено», «совпадений нет», «нужен контекст», «инцидент не найден». Ошибка чтения архива обрабатывается отдельно от пустой выдачи. В каждом совпадении передай фактические `id`, архивную `version`, `title`, `state`, `resolvedAt`, `present`, краткие `symptom` и `solution`, а также краткое основание сходства из проверяемых полей. `symptom` и `solution` могут быть `null`. Укорачивай исходный текст без изменения смысла. Поле «Что сделали» или «Результат» в ответе можно заполнить только фактами из записанного решения. Пустое решение остаётся пустым даже у завершённой записи.
- Для ссылки передай D70 проверенный ID и доступный штатный адрес, полученный из принятой записи или серверной настройки ITSM. При отсутствии внешнего адреса используй стабильный адрес реестра `/itsm/incidents/${encodeURIComponent(id)}`. В веб-приложении он строится существующим `ticketPath(id)` из `apps/web/src/itsm/api.ts`. Соответствующий GET имеет префикс `/api/v1`. Для результата с `present: false` карточка тоже должна открываться. Содержимое описаний, решений и произвольных полей обрабатывай как данные ITSM. D60 выполняется локально. Вызов провайдера и минимальный набор передаваемых фактов задаёт D70.

## Приёмка и передача D70

Начни с `apps/api/tests/itsm.test.ts`, `apps/api/tests/analysis.test.ts` и `packages/analysis/tests/`. Проверь выборку на SQLite во временном каталоге через штатное принятие синтетической выгрузки. Для правил ранжирования используй небольшие воспроизводимые случаи. Убедись, что предыдущий анализ инцидента продолжает проходить свои тесты.

| Случай | Ожидаемый результат |
| --- | --- |
| Открытая заявка и два подтверждённых аналога | Возвращаются оба реальных ID с проверяемыми симптомами и решениями. ID исходной карточки исключён |
| Ранее завершённая заявка исчезла из текущего JSON | Архивный аналог находится, его карточка доступна по GET со строковым ID |
| `Research` с датой и решением, активная с решением, повторно открытая заявка | Эти записи не появляются в выдаче |
| Завершённая запись без даты либо решения | Неизвестное поле остаётся `null`. Другие подтверждённые поля доступны |
| Похожие детали, но разные даты и ID | Порядок стабилен на одинаковых архивных данных. Предельное число результатов соблюдено, лучший более старый аналог доступен |
| Симптомы без ID, пустой запрос, неизвестный ID и запрос без совпадений | Поиск по содержательным симптомам работает. Остальные случаи дают различимые явные результаты |
| Правка только `solution`, перезапуск, повторная обработка той же выгрузки | Изменение видно при следующем запросе, при повторе и перезапуске нет дублей или устаревшей выжимки |
| Сложный ID, например `SYN-D60/01` | Связанный GET с `encodeURIComponent(id)` возвращает эту карточку, включая архивный случай |

**Сдать** принятый SHA D40 и SHA реализации, файлы реализации и проверок, команды и их фактические результаты, пример запроса и типизированного ответа с синтетическими данными и доступными ссылками. Передай D70 имя функции, её реальные типы и точку вызова на сервере. Запусти `npm run check`, целевые тесты и `npm test` из корня по доступности.
