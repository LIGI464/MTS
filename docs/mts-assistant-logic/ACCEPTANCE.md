# Промт для Cursor · приёмка помощника

На Node 24 выполни `npm ci`, `npm run check`, `npm test`, `npm run build` и `npm run test:e2e`. Используй временный каталог данных, синтетические выгрузки и локальный мок Responses API. Для живой проверки используй настроенный тестовый ключ и демоданные при наличии доступа. В отчёте указывай результаты моков и живой проверки отдельно.

| Сценарий | Что проверить |
| --- | --- |
| Вопрос действительно доходит до модели | Введи с «Пульта» «Что просрочено?» и в карточке «Как проявляется сбой?». Мок проверяет метод, модель, системный промт, точный вопрос, права и факты из JSON. Верни разные тексты для двух вопросов и проверь, что оба появились в UI с `source: "llm"`. |
| Ответ по заявке без аналогов | У заявки известны срок и сервис, подходящих аналогов нет. Помощник отвечает на «Когда срок?» фактом из принятой версии. На «Почему это произошло?» без подтверждённой причины указывает, каких данных не хватает. |
| Несколько JSON и версии | Помести нужный факт во вторую настроенную JSON-выгрузку и проверь ответ по её ID. Примени обновление через действующий маршрут импорта и проверь, что после смены ревизии виден новый факт. Убедись, что помощник находит координатора из справочника и отвечает при отсутствии необязательного поля. Дубль ID в архиве и текущем файле учитывается один раз. |
| Полный обход | Выбери заявку с подтверждённым симптомом. Помести сильное совпадение из отдельного JSON в конец набора, другое — среди активных заявок, третье — в архиве вне текущего снимка. Добавь более пяти слабых записей с общим заголовком. Перемешай входные данные, сузь видимый фильтр пульта. Проверь число реально обработанных уникальных ID, отсутствие самой заявки и одинаковый верх выдачи. Проверь, что лимит применяется к результату после обхода. |
| Явное сравнение пары | Открой A и задай «Сравни с B». В запрос к модели входят A и B, а в ответе есть подтверждённое сходство и важное различие. Для неизвестного второго ID помощник просит проверить номер. Активная запись сохраняет свой статус, историческое решение связано с исходным завершённым случаем. |
| Продолжение разговора | В одном чате спроси «Были похожие случаи?», затем «Что помогло в первом?». Проверь факт из нужного аналога. Открой другую карточку с задержанным ответом первой. Убедись, что данные первой не появляются во второй. Проверь такой же сценарий в общем чате. |
| Роль и стиль | Сверь ответы с пульта, карточки и повторного запроса. Ответ на русском начинается с сути, шаги появляются по необходимости. Просьба сменить роль или текст с командами в исходном JSON не меняет поведение и не раскрывает служебные данные. |
| Отказ источника и модели | Повреди один JSON, повтори поиск и проверь метаданные охвата. Смоделируй тайм-аут, HTTP 500, невалидный JSON и выдуманный ID в ответе модели. Проверь корректный резервный режим. Неверный операторский токен возвращает 403. |
| Регрессии D60–D90 | Проверь действующий архивный поиск, импорт и SSE, одиночный анализ, два входа в чат, переходы в ITSM и восстановление фокуса. Код чтения чата и сравнения сохраняет исходные заявки. |

Сдай SHA, таблицу результатов команд и сценариев, пример ответа на произвольный вопрос, пару реплик продолженного диалога и пример сравнения. Для сравнения приложи число уникальных записей, которое сервер фактически обработал. Если живой ключ отсутствовал, зафиксируй это рядом с результатами теста транспорта.
