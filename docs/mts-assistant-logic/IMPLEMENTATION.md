# Промт для Cursor · подключение помощника

Работай поверх D90 из `Cursor/assistant-analysis`. Доработай существующий маршрут `POST /api/v1/assistant/chat`, серверный поиск и имеющиеся два режима панели. Подключи системный промт и дополнение сравнения из этого комплекта. [Системный промт](PROMPT-SYSTEM.md) · [Сравнение](PROMPT-COMPARISON.md)

## Данные JSON и архив

1. Найди и опиши фактические JSON-источники инцидентов и справочников. Включи текущий `character_problems.json` из настроенного `MTS_DATA_DIR`, принятые импорты, сохранённый архив ITSM в `dashboard.sqlite` и `coordinators.json` при наличии. `baseline.json` и `data/demo/character_problems.json` используй в соответствующем деморежиме через существующий запуск и импорт. Для дополнительных JSON-выгрузок инцидентов в рабочем наборе используй серверный список настроенных источников и существующую нормализацию. Проверь, что помощник может получить данные из каждого подключённого набора. Обычные файлы проекта и конфигурация окружения остаются за границей данных ITSM.
2. Разбирай структуру JSON на сервере. Используй схемы, нормализацию и версионирование репозитория. Храни привязку к источнику и принятой версии. Преобразуй исходные поля в ID, название, сервис, симптомы, состояние, сроки, влияние, решение и разрешённые справочные данные. Даты, статусы, численность и SLA рассчитывай существующими правилами. Известное отсутствие поля передавай как `null`.
3. Собирай согласованный набор на принятой ревизии. Объединяй активные и архивные записи по ID. Для текущих фактов выбирай актуальную принятую запись, для исторических вопросов обращайся к версиям. Один файл, импортированный затем в архив, не увеличивает счётчик. После импорта, обновления JSON или сброса исключай устаревшие контексты и кэш. Повреждённый файл обрабатывай по правилам последней пригодной версии и передавай её актуальность в ответ. Сбой одного источника отмечай в охвате.
4. Получай факты через серверный слой с действующими правами доступа. Передавай модели ограниченные проекции записей и нужные агрегаты. Доступ к файлам идёт через подготовленные источники. Произвольный путь из чата, содержимое конфигурации и ключи API исключены из данных запроса.

## Запросы и контекст чата

- Определи, что хочет оператор. Обрабатывай вопросы о карточке, сроке и статусе, вопросы по пульту, поиск по симптомам, сравнение по ID и поиск аналогов. Для точного ID ищи по текущим и архивным данным. Для количества, списка, сроков и приоритетов сначала вычисляй запрошенный результат по принятому набору. Передавай модели результат и метаданные охвата. Вопрос о статусе или сроке работает даже при пустом результате поиска аналогов.
- Закрепляй режим карточки за выбранным ID и серверной версией. Если оператор назвал второй ID при сравнении, сохрани выбранную заявку как первую и загрузи вторую. При запросе из общего чата один явно указанный ID становится контекстом запроса, а пара явно названных ID разрешается как пара. Для общего поиска без ID используй введённые симптомы. Уточняй ссылку, которую нельзя однозначно разрешить.
- Передавай ограниченную историю конкретной беседы и проверенные ссылки на упомянутые записи. Обновляй факты в начале каждого запроса. Состояние общего чата, карточки A и карточки B должно быть раздельным. Связывай ответ с идентификатором запроса, беседой и версией до применения в UI. Для повторной отправки используй контекст исходного запроса. При смене выбранной заявки или сбросе поздний ответ не показывается в новой беседе.

## Полное сравнение

1. Выбери исходный случай из подтверждённого ID, пары или описания симптомов. Для поиска аналогов сформируй полный набор уникальных заявок из всех принятых источников, без ограничения видимыми очередями, статусом `Closed` или первой страницей. Зафиксируй ревизию набора и исключи саму выбранную заявку.
2. Сопоставь исходную заявку с **каждым** оставшимся ID. Переиспользуй `findSimilarIncidents` и проекции архива там, где они подходят. Дополни сравнение активными записями. Учитывай сервис и операцию, описание, признаки отказа, коды ошибок, условия и влияние. Нормализуй варианты написания и известные эквивалентные формулировки. Учитывай достаточность фактов. Вычисляй единый порядок после обработки всех записей, включая пакетную обработку большого набора. Лимит пяти карточек D90 применяется к выдаче после сравнения. При равенстве используй стабильный порядок, например по дате и ID. Для явного сравнения двух заявок получи именно эту пару и те же поля сравнения.
3. Передай модели выбранную запись или пару, краткие факты верхних кандидатов и охват. Охват включает ревизию, число доступных и проверенных уникальных записей в выбранном объёме, использованные источники и признак полноты. Счётчик увеличивается при реальном рассмотрении записи. Если обход прерван или источник недоступен, верни частичный результат с объяснением. Статус «совпадений нет» требует завершённой проверки доступного объёма.
4. Показывай завершённые аналоги в действующих карточках `matches`, с разрешёнными ссылками и записанным решением. Для активных совпадений используй типизированные ссылки на реальные заявки с фактическим статусом. Сохрани совместимость входа D90 и правила перехода к заявке.

## Ответ через API модели

- Используй действующий `requestProviderText` и Responses API по настроенному адресу `CODEX_SALE_BASE_URL`. Живой режим использует `MTS_AI_MODE=live`, `CODEX_SALE_MODEL`, серверный `CODEX_SALE_API_KEY` и действующую авторизацию `MTS_OPERATOR_TOKEN`. Для каждого нового подходящего сообщения в авторизованном живом режиме передавай вопрос, историю нужной беседы и подготовленные факты модели. Ключ остаётся на сервере. Чат показывает сформированный моделью ответ с `source: "llm"` после валидации.
- Передавай системные инструкции отдельно от вопроса и JSON средствами провайдера. Проверь поддержку формата на тестовом Responses API. Добавляй промт сравнения для сравнения пары и поиска аналогов. Для унификации стиля обоих режимов используй один системный промт.
- Подготовь структурированный контекст с `question`, `history`, выбранной заявкой, фактами для вопроса, кандидатами и охватом. Отделяй последние реплики от проверенных сведений. Сообщай о просрочке и ближайшем сроке по серверному времени и принятым правилам SLA.
- Проверь модельный JSON по строгой схеме и сверяй `evidenceIds` с разрешёнными записями запроса. Преобразуй проверенные ссылки на данные в существующие поля ответа API. Статусы, числа, карточки и ссылки строит сервер. Шаблоны и запасной режим не получают `source: "llm"`. При отключённой модели, тайм-ауте и ошибке показывай доступные факты и ясный статус режима. Кэш учитывает ревизию данных, контекст беседы, вопрос, версию промта и режим доступа.
- Сохрани ограничение запросов, обработку неверного токена, SSE, импорт, журнал «События» и поведение существующего анализа отдельной заявки. [Проверки](ACCEPTANCE.md)
