# Контракт для двух рабочих веток

Это дополнение к [контракту v1](../mts/CONTRACT.md). Одинаковые пути и поля позволяют Cursor собрать формы на фикстурах, пока Astra реализует сервер. Новые маршруты ниже — задание на обновление. Уже в рабочем релизе есть `GET /api/v1/dashboard`, поток `/api/v1/events`, анализ и сброс.

## Данные кейса

В `character_problems.json` лежит массив из **44** различных номеров: 14 Assigned, 10 WorkInProgress, 10 Resolved, 5 Closed, 5 Research. По приоритетам — 16 с уровнем 1, 23 с уровнем 2, 5 с уровнем 3. Во всех 44 имеется текст `solution`. Все пять Research имеют `completionDate`, у трёх записей отсутствует дедлайн. Эти числа нужны для приёмки именно выданной версии файла. Архив работает с любым валидным массивом контракта, включая пустой.

| Поле выгрузки | Значение в интерфейсе и хранении |
|---|---|
| `id`, `sysId` | Номер заявки и идентификатор системы. `sysId` — строка, может превышать безопасное целое JS. `id` служит ключом стабильной локальной ссылки. |
| `header`, `description`, `shortDescription`, `solution` | Название, первоначальное описание, краткое описание и текст решения. Показать записанный текст и для активной заявки. При отсутствии решения написать «Решение не указано». |
| `stateEnum`, `state`, `stateId`, `completionDate` | Состояние определяет существующая `incidentState`. В справочнике расходятся числовые коды завершённых состояний с выгрузкой. Для записи решения использовать действующее соответствие из `demo/steps.ts`. |
| `priorityId`, `priority`, `impactId`, `urgencyId` | Наивысший = 4, высокий = 3. Явные числа и подписи сохраняются. Пустое значение поля отличается от нуля. |
| `productName`, `service`, `scenarioName`, `assignedGroupName`, `assignedEmployee` | Продукт, сервис, сценарий, группа и исполнитель. Длинные значения и отсутствие исполнителя допустимы. |
| `submitDate`, `deadline`, `lastAssignmentToTeamDateTime` | Храним исходные значения, рабочие даты показываем в Europe/Moscow. Служебные поля, строковые ID и неизвестные атрибуты переживают точечную правку. |

`incidents_attributes.json` — справочник из 30 строк с ключами `api_source`, `description`, `possible_values`. Его используют для подписей и сверки. Вторая очередь инцидентов из справочника не создаётся. В публичном Git — синтетические фикстуры. Оригиналы подключаются из локального каталога с данными.

## Архив и источник

1. Рабочий источник пульта — валидный JSON-массив в `MTS_DATA_DIR/character_problems.json`. За его чтение, атомарные замены и SSE отвечает существующий runtime. Исходная копия `baseline.json` используется для восстановления демо.
2. При первом успешном чтении сервер переносит **каждую** строку в локальный реестр SQLite в том же постоянном каталоге. Сохраняются оригинальные поля записи, её активность в текущем файле и версии с временем наблюдения. Обработка относится и к изменениям внешним редактором. Целевой ID новой критической записи виден и в JSON, и в ITSM.
3. Отдельная версия создаётся при изменении содержимого записи, включая один только `solution`, либо при появлении/исчезновении. Перестановка строк и ключей, повторный poll и перезапуск с тем же файлом не создают истории. Возврат из B в A после A → B остаётся самостоятельным событием. Запись последнего валидного снимка и изменение архива выполняются одной транзакцией SQLite.
4. Исчезновение из валидного массива и сброс демо сохраняют старую ссылку, записанные решения и историю. Для записи вне текущей выгрузки интерфейс показывает «В архиве». Правки по ней возвращают понятный конфликт. Битый или отсутствующий JSON сохраняет последнее принятое состояние. Первичная миграция старого `dashboard.sqlite` прогоняет полную текущую выгрузку даже при совпадающем старом снимке.
5. Кнопки сценариев и сохранения решения проходят через существующую последовательную очередь runtime. Проверь ожидаемую версию исходной строки после перечитывания файла, в том числе при внешней правке. Сначала сформируй и провалидируй полный новый массив, сохрани его атомарно и проведи тот же путь принятия, что при ручной правке. Обработай сбой SQLite/файла и восстановление после остановки процесса. SSE подтверждает принятую ревизию. Адрес API, токен и сырые записи отсутствуют в журналах браузера сессии.

## HTTP

Префикс у всех новых серверных маршрутов — `/api/v1`. В таблице он опущен. Формат ошибки — действующий `{code,message}`. Локальные GET доступны с теми же правами чтения, что пульт. Мутации требуют существующий Bearer `MTS_OPERATOR_TOKEN` на сервере. При отключённом операторе действует политика существующего reset (404), при неверном/пустом токене на включённом стенде — 403. Остальные ошибки — 400 для ввода, 404 для неизвестного ID, 409 для устаревшей версии/недоступного источника или недопустимого перехода.

| Метод и путь | Вход | Выход |
|---|---|---|
| `GET /itsm/incidents` | Без параметров. Для объёма кейса поиск на клиенте | `{items: TicketSummary[]}`, одна строка на номер, включая архивные. |
| `GET /itsm/incidents/:id` | URL-кодированный номер | `{ticket: TicketSummary, description, solution, history: HistoryEntry[], rawFields}`. |
| `GET /coordinators` | Без параметров | Массив `[{id, name}]`. Оба поля — непустые строки. |
| `POST /itsm/incidents/:id/coordinator` | `{coordinatorId, expectedVersion, requestId}` и Bearer | `{id, version, revision}`. `expectedVersion` берётся из `ticket.version`, `requestId` — UUID. |
| `POST /dev/scenarios` | Команда из таблицы ниже и Bearer | `{id, version, revision}` после успешной записи; `version` — текущая непрозрачная версия заявки. |
| `POST /itsm/incidents/:id/resolve` | `{requestId, expectedVersion, solution}` и Bearer | Такой же результат мутации. Текст trim, 1–1000 символов; записан в поле `solution`, указаны `completionDate`, `stateEnum`, метка и код по релизу. |
| `POST /demo/reset` | Существующий маршрут и Bearer, после подтверждения в UI | Существующий Snapshot. Архив остаётся доступным. |

`TicketSummary` содержит `id, version, title, product, service, team, assignee, state, stateLabel, priority, createdAt, dueAt, resolvedAt, present`. Форматы полей совпадают с текущим `Incident`. Поле `present` имеет тип boolean, дополнительное `hasSolution?: boolean` сообщает о наличии исходного текста. `description` и `solution` имеют тип `string | null`. `HistoryEntry` содержит `version, at, present, stateLabel, team, dueAt, priority, description, solution`. Время `at` — время наблюдения сервером. Каждая версия сохраняет текст решения на тот момент. Сервер возвращает историю от новых изменений к старым.

`rawFields` содержит все ключи последней сохранённой исходной строки, в том числе для заявки в архиве. Значения передаются как JSON с исходными типами, включая неизвестные ключи, строковые идентификаторы, `null`, `false`, `0`, пустой `deadline` и служебный `waitingExitDate`. Для рабочего состояния используется `stateEnum`; в `rawFields.stateId` сохраняется, например, исходное `7` для `Resolved` или `10` для `Closed`.

В `Incident`, `TicketSummary` и `HistoryEntry` доступно `coordinator?: {id, name} | null`. Пропуск поля и `null` означают отсутствие персонального назначения и поддерживаются для старых снимков и фикстур. У записи из источника начальное назначение выводится при точном совпадении `assignedGroupName` с `COORDINATOR_TEAM` и непустом `assignedEmployee`. Явное назначение хранится в SQLite отдельно от исходной группы и исполнителя. Сценарий `assign` меняет группу по правилам D21.

Справочник читается при старте из `MTS_DATA_DIR/coordinators.json` в формате массива для `GET /coordinators`; идентификаторы и имена уникальны. При отсутствии файла список строится из сотрудников группы `COORDINATOR_TEAM` в текущей принятой выгрузке. В исходной карточке сотрудник из этой группы отображается и при отсутствии его имени в настроенном справочнике. Новое назначение принимает только идентификатор из текущего справочника. Неизвестная заявка или идентификатор координатора дают 404 (`NOT_FOUND` или `COORDINATOR_NOT_FOUND`), архивная заявка или конфликт версии — 409 (`TICKET_ARCHIVED` или `VERSION_CONFLICT`).

При изменении персонального назначения сервер добавляет версию в историю и отправляет SSE `event: dashboard` с полным `Snapshot`, принятой `revision` и уведомлением `coordinator.changed` с `incidentId`, `title`, `at` и `seq`. `coordinator.assigned` обозначает прежнее событие входа заявки в очередь группы координаторов.

| `action` у `POST /dev/scenarios` | Дополнительные поля | Результат |
|---|---|---|
| `create-critical` | `requestId` — UUID этого намерения | Новая синтетическая строка в формате выгрузки. Сервер назначает новый уникальный ID, текущие даты, приоритет 4, активный статус, команду вне координаторов. Количество записей увеличилось на одну. |
| `escalate` | `requestId, id, expectedVersion` | Выбранная активная запись получает приоритет 4 и соответствующую подпись. |
| `assign` | Те же | У выбранного ID команда становится `КЦ ИТ Координаторы Массовых Инцидентов`, назначение сотрудника согласовано с новой группой. |
| `deadline` | Те же плюс `deadline` — конкретная UTC-дата | Меняется только срок выбранного ID. Страница предлагает «через 90 секунд» и даёт выбрать другое время. |

Одинаковый `requestId` для идентичной повторной команды возвращает тот же результат и запись. Иное тело с уже занятым ключом возвращает 409. Это относится и к решению по карточке ITSM. Версия привязана к записи и её присутствию, поэтому правка другого инцидента не блокирует пользователя. Устаревшая форма предлагает перечитать карточку и сохраняет введённый оператором текст. Один ID занимает одну карточку в очереди приоритета и одну строку реестра. Старые группы в снимке сохраняются для совместимости.

## Импорт JSON · D24

| Метод и путь | Вход | Выход |
|---|---|---|
| `POST /incidents/import/preview` | `{fileName, jsonText}` и Bearer. Имя файла и его содержимое — строки. | `{valid, errors, total, byPriority, added, updated, archived}`. При `valid: true` добавляются `previewId` и `expectedRevision`. |
| `POST /incidents/import/apply` | `{previewId, expectedRevision, requestId}` и Bearer. `requestId` — UUID. | `{revision}` после принятия файла. |

`errors` — массив сообщений. Он пуст при валидном предпросмотре. Невалидный содержит хотя бы одну ошибку. `total` — число элементов массива, `byPriority` — счётчики распознанных приоритетов по ключам `"1"`, `"2"`, `"3"`, `"4"` для низкого, среднего, высокого и критического приоритетов. Все счётчики и ревизии — неотрицательные целые. Максимальный размер тела запроса предпросмотра — 2 МиБ.

`added`, `updated`, `archived` сравнивают загружаемый файл с текущей принятой выгрузкой. Возвращённая из архива заявка считается добавленной, правка исходного поля — изменением. Порядок строк и ключей на сравнение не влияет. При невалидном файле счётчики изменений равны нулю. Пустой валидный массив архивирует все текущие записи.

Предпросмотр проверяет файл без записи. `previewId` — непрозрачная строка, действующая до применения, перезапуска или истечения 10 минут. Сервер хранит до 16 последних предпросмотров. Для недоступного предпросмотра применяется `409 PREVIEW_UNAVAILABLE`. Если база предпросмотра устарела, применяется `409 REVISION_CONFLICT`.

Применение атомарно заменяет рабочую выгрузку и принимает её в архив с сохранением `baseline.json` для сброса. При отсутствии или повреждении рабочего файла базой служит последний принятый снимок. После изменения записей сервер отправляет SSE `dashboard` с принятой ревизией. Повтор идентичной команды с тем же `requestId` возвращает сохранённую ревизию, в том числе после перезапуска. Повторное использование `requestId` для другого действия даёт `409 REQUEST_ID_CONFLICT`.

## Переходы и совместимость

- И доска, и диалог показывают действие «В ITSM». При корректном серверном `MTS_ITSM_URL_TEMPLATE` используется прежний внешний HTTPS URL с `{id}` или `{sysId}`. Во всех остальных случаях React формирует `/itsm/incidents/` + `encodeURIComponent(id)`. Ссылки открываются в новой вкладке с `rel="noopener noreferrer"`. `productUrl` не определяет переход.
- Пульт читает снимок и тот же SSE. В автономном `dev:web` тестовые режимы явно помечены. Полный сценарий с записью проверяют на Fastify и постоянных данных.
- Текущий CLI `demo:step critical` повышает приоритет существующей заявки, `deadline` выбирает другой активный ID автоматически. Сохраняем совместимость CLI. Формы разработчика адресуют выбранный ID и отдельно реализуют создание новой заявки.
