# D21 · Критическая заявка, назначение, срок и решение

**Промт для Astra 6.2, после D20.** Добавь серверные действия из [контракта](CONTRACT.md). Зона записи — сервер, его тесты и собственные типы ITSM. Прочитай `apps/api/src/demo/steps.ts`, `source/index.ts`, `source/file.ts`, `http/operator-token.ts`. Переиспользуй валидацию, атомарную запись и очередь runtime.

1. В `POST /api/v1/dev/scenarios` принимай только перечисленные действия и поля. `create-critical` добавляет **новый** валидный инцидент с уникальным номером, приоритетом 4 и свежими UTC-датами. Прежние четыре CLI-команды работают по-прежнему. Для `assign`, `deadline` и `escalate` бери именно выбранный ID. Сохрани метку, код, дату назначения и обязательные поля согласованно.
2. Реализуй `POST /api/v1/itsm/incidents/:id/resolve`. Запиши фактический текст, время завершения и статус в живую строку выгрузки. Инцидент уходит из активной очереди на обычном потоке; из архива доступны прежнее и новое решение. Внешняя правка JSON до/после через watcher даёт тот же видимый результат. Пользовательское решение остаётся отдельным от ответа ИИ.
3. Используй существующую проверку Bearer. Проверяй разрешение и вход до изменений. Для одного намерения с одинаковым `requestId` верни исходный ответ без дубликата. Чужое тело с тем же ключом и устаревшая `expectedVersion` дают 409. Защити запись от одновременных команд и частичной ошибки: проверка версии и запись внутри единой очереди, полный валидный массив, неизменный baseline, восстановление после сбоя и повторного запроса.
4. Покрой тестами пустое решение, неизвестный ID, отсутствие прав, два запроса на создание с одним UUID, две гоняющиеся правки одной версии, независимые ID и сброс. Проверь содержимое исходного файла и последующий снимок/историю после перезапуска. В JSON сохраняются все посторонние атрибуты.

**Сдать** серверный SHA, точные контрактные примеры на синтетическом ID, результаты `npm run check`, целевых тестов и порядок живого прогона. Серверное действие считается успешным после сохранения.
