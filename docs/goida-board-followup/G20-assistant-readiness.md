# G20 · Неустойчивый ответ по локальным правилам

**Промпт для Cursor.** Воспроизведи случай, когда с тем же действующим токеном одна карточка получает ответ модели, а другая эпизодически показывает локальный ответ. Задержка ITSM — гипотеза. Сверь `apps/web/src/main.tsx`, `assistant/assistant-host.tsx`, клиент запроса, `apps/api/src/assistant/index.ts`, `resolve.ts`, `sources.ts`, конфигурацию live-режима и тесты помощника.

1. Запиши последовательность событий для первого запроса из деталей. Сопоставь ID, версию, ревизию данных, наличие авторизации без значения токена, готовность контекста, доступность источника, кэш, итоговый режим и причину fallback. Раздели ожидание данных, неверную авторизацию, выключенную модель, ошибку/тайм-аут провайдера, лимит и ответ для устаревшего запроса.
2. Исправь подтверждённую причину. Если запрос стартует до готовности контекста, покажи состояние загрузки и отправь первоначальный запрос один раз по готовности. Если нужен повтор после загрузки или восстановления источника, привяжи его к ID, версии и актуальному запросу. Старый ответ не подменяет ответ другой заявки. Проверь, что локальный результат раннего запроса не перекрывает допустимый live-запрос после изменения готовности или авторизации.
3. Сохрани правдивое обозначение режима и существующую проверку прав. При реальном отказе провайдера покажи нормальный резервный ответ с понятной причиной или действие «Повторить». Не выводи токены и сырые данные заявки в логи.

**Приёмка.** На моках воспроизведи медленное появление заявки, быстрый переход A → B, валидный токен в обеих карточках, недействительный токен и серверный отказ. Сдай причину, исправление и результат каждого сценария.
