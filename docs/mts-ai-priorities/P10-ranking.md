# P10 · Расчёт рекомендаций

Продолжай рабочую ветку P00. Сделай серверный расчёт общей ленты заявок, которыми оператору стоит заняться сейчас. Проверь `apps/api/src/analysis/index.ts`, `packages/analysis/src/index.ts`, `packages/analysis/src/provider/index.ts` и конфигурацию `apps/api/src/http/config.ts`. Переиспользуй текущий серверный провайдер и правила его доступа. Существующий маршрут анализа отдельной заявки используй для просмотра деталей.

## Вход и порядок

- Строй кандидатов из всего последнего принятого снимка, включая заявки за пределами текущего поиска, фильтра и видимой области. Учитывай состояния, группы, `getSlaState`, срок и доступные признаки влияния из данных заявки. Завершённые и закрытые записи исключай из рабочих рекомендаций. Исследование рассматривай при наличии требуемого действия оператора и доступной очереди. Дедуплицируй по ID.
- Определи, какие заявки требуют действий сейчас, и верни общий порядок от самых важных. Влияние, блокировка операции, просрочка и близкий срок влияют на решение вместе с приоритетом ITSM. Выдай обоснованный ответ и для случая, когда подходящих записей нет. Если для размера контекста нужно оценивать части набора, обойди все рабочие записи, сравни оценки и собери единый порядок. Ограничение видимых карточек применяй к итоговой выдаче.
- Обоснование на русском должно кратко называть факт и его влияние на срочность. Срок, состояние и числа бери из принятой версии. При нехватке данных давай сдержанное обоснование по доступным признакам. Поля выгрузки трактуй как данные. В запрос к модели передавай только нужный нормализованный контекст. Доступы и внутренние сведения остаются на сервере.
- Лента возвращает рекомендации для чтения. Место в ней и приоритет ITSM представлены как разные поля. При равной оценке используй воспроизводимый порядок, например по сроку, затем по ID.

## Контракт и обновление

- Добавь один маршрут для общей выдачи, например `POST /api/v1/incidents/priorities`. Сервер получает снимок из runtime. Запросы из браузера используют действующий порядок авторизации для живого ИИ. При неуказанном токене лента может получить расчёт по локальным правилам. Неверный переданный токен обработай по принятому контракту API.
- В общей выдаче передай ревизию или однозначный маркер входного снимка, время оценки и источник `llm` или `rules`. В каждой позиции передай ID, версию заявки, место в списке, короткое обоснование и пригодную цель для навигации. Заголовок, статус, приоритет и SLA сверяй с текущим снимком. Используй строгую схему и проверку принадлежности ID перед показом. Учитывай дубликаты, архивирование и устаревший ответ.
- Пересчитывай при новой принятой выгрузке и значимых переходах SLA с разумной частотой. Связывай ключ кэша с входным снимком и режимом доступа к модели. Объединяй одинаковые расчёты, ограничь параллельные запросы и время ожидания. Ререндер, открытие карточки и повтор того же кадра SSE используют готовый расчёт. После сброса отбрасывай ответы от предыдущего набора.
- При выключенном или недоступном провайдере используй детерминированные локальные правила с теми же признаками срочности. Для ответа правил покажи его источник. При пустом снимке верни пустой список и используй состояние «Нет заявок, требующих действий сейчас». При ошибке временно показывай последний пригодный результат с отметкой состояния.

## Проверить и сдать

На демоданных проверь полный вход и ранжирование, в том числе существенную заявку за пределами первой экранной порции. Проверь низкий приоритет с подтверждённым влиянием, ближайший срок, просрочку, пустой набор, посторонний ID в ответе модели и потерю связи. Используй мок провайдера и тесты локальных правил. Проверь устаревший ответ после новой выгрузки или сброса и работу одиночного анализа. Запусти `npm run check` и затронутые тесты. Покажи пример валидной общей выдачи на демонаборе, укажи результаты команд и SHA. Дождись подтверждения перед P20.
