# T42 · Исполнитель 2 · Разверни релиз на VPS

Выполни этот промт со своего ПК. Входные данные · проверенный SHA T51, хост, именной SSH-доступ, место для данных, HTTPS-поддомен и конфигурация модели при наличии. За выдачу доступов отвечают владельцы сервера и домена. Для операций с Docker и системным прокси используй полномочия, согласованные с владельцем VPS. [Памятка по доступам](../ACCESS.md). Используй готовые файлы из T41. Цель · работающий публичный стенд и проверка первого кадра SSE.

1. Сверь доступ и занятость портов. Выбери свободный loopback-порт для контейнера и работай в каталоге приложения. Если хост уже обслуживает другие проекты, используй его резервный порт и существующий reverse proxy. Обнови только конфигурацию нового виртуального хоста. Запиши предыдущий тег этого приложения и состояние здоровья для отката.
2. Сделай checkout строго по релизному SHA. Создай постоянный каталог для JSON и SQLite с правом записи от пользователя контейнера. Установи `MTS_HOST_DATA_DIR`, `MTS_HOST_PORT` и `MTS_IMAGE_TAG` в закрытом env-файле на хосте. При первом запуске на реальной выгрузке положи авторизованную копию в постоянный каталог под именем `import.json`, доступным контейнеру. Команда импорта создаст живой файл и baseline через тот же валидатор. Сохраняй существующий рабочий набор между обновлениями. Для нового стенда разрешено начать с синтетической фикстуры.
3. Задай секреты через окружение хоста · `MTS_OPERATOR_TOKEN`, `CODEX_SALE_API_KEY`, `CODEX_SALE_MODEL`, `MTS_AI_MODE` и при наличии `MTS_ITSM_URL_TEMPLATE`. ID модели из каталога `GET /v1/models` для предоставленного ключа. Секреты не выводятся ни в консольный отчёт, ни в Git. Если ключа или модели нет, оставь `rules` для локального режима.
4. Из каталога репозитория выполни команды ниже. `MTS_VPS_ENV` — абсолютный путь env-файла, а тег соответствует релизному SHA. Строку `run` выполняй только при первом старте на предоставленном `import.json`. Для синтетического набора `ensureDemoData` подготовит том при старте.

```bash
docker compose --env-file "$MTS_VPS_ENV" -f deploy/compose.yaml build dashboard
docker compose --env-file "$MTS_VPS_ENV" -f deploy/compose.yaml run --rm --no-deps -T dashboard npm run data:load -- --file /app/data/runtime/import.json
docker compose --env-file "$MTS_VPS_ENV" -f deploy/compose.yaml up -d --no-build
docker compose --env-file "$MTS_VPS_ENV" -f deploy/compose.yaml ps
docker compose --env-file "$MTS_VPS_ENV" -f deploy/compose.yaml exec -T dashboard node deploy/smoke.mjs http://127.0.0.1:8787
```

5. Подключи HTTPS через текущий прокси и проверь его конфигурацию перед перезагрузкой. Проверь `node deploy/smoke.mjs https://<домен>` с Node 24 на доступном ПК или через `docker compose exec` и открой `https://<домен>/admin/incidents`. По разрешению владельца выполни один платный анализ и зафиксируй, что UI показал «codex.sale». Проверка файла и уведомлений выполняется по T52.
6. Если сборка или smoke релиза падают, восстанови предыдущий тег через Compose без удаления тома и проверь `/healthz` и SSE. Зафиксируй причину. Если отсутствует маршрут HTTPS, доведи доступную loopback-проверку и укажи, какой параметр нужен для публикации.

**Результат.** Дай URL, SHA и результаты REST, SSE и live-модели. Укажи, где на хосте менять JSON для демонстрации и какой тег использовать для отката. В отчёте приводятся пути и статусы без значений ключей.
