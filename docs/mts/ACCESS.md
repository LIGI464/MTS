# Два исполнителя · Роли, доступы и передача релиза

Обе Astra 6.2 работают в облаке только с GitHub-репозиторием `LIGI464/MTS`. Репозиторий, общий SHA и промт — их входы. Сдача — ветка или PR, SHA и результат доступных проверок. Реальную выгрузку, VPS, DNS и ключи обслуживают люди.

## Исполнитель 1 · LIGI464 · ПК 1, Cursor, Astra A и интеграция

- **От него нужны** GitHub-ник, рабочий локальный checkout с Node.js 24 и браузер для проверки. GitHub-владелец может использовать свой прежний доступ.
- **Работа** · выполняет [B00](00-foundation/B00.md), сливает основу и пересылает общий SHA второму исполнителю. Ведёт локальный Cursor по [B10](10-web/B10.md). Со своего ПК запускает облачный чат №2 с Astra A по [B20](20-api/B20.md) в ветке `feat/api`. Принимает PR обеих Astra и собирает релиз по [T51](50-integration/T51-integrate.md).
- **Что сдаёт** · релизный SHA, результаты сборки, тестов и локальной проверки на ПК 1. Передаёт этот SHA второму исполнителю для VPS.

## Исполнитель 2 · Nekori123123 · ПК 2, Astra B и стенд

- **От него нужны** GitHub-ник, SSH-публичный ключ Ed25519 в файле `.pub` и подтверждение, что он берёт T42. Если он сам владелец VPS и уже входит по ключу, использует имеющийся доступ.
- **Работа** · запускает облачный чат №3 с Astra B по [B30](30-ai/B30.md) в `feat/analysis` и [T41](40-release/T41-package.md) в `feat/deploy`. Использует общий SHA B00, переданный исполнителем 1. Проверяет отчёт Astra B и передаёт её PR исполнителю 1. После T51 разворачивает утверждённый SHA по [T42](40-release/T42-vps.md).
- **Что сдаёт** · публичный HTTPS-адрес `/admin/incidents`, развёрнутый SHA, результаты `/healthz`, SSE и live-анализа, если настроен ключ. Указывает используемый reverse proxy, доступность предыдущего образа для отката и каталог рабочего JSON. В [T52](50-integration/T52-rehearse.md) меняет файл на VPS и вместе с первым исполнителем проверяет оба экрана.

## Кому и как выдавать доступ

| Доступ | Получатель и выдача |
|---|---|
| GitHub · люди | Владелец `LIGI464/MTS` приглашает второго исполнителя по его нику в `Settings → Collaborators → Add people`. Для личного репозитория роль Collaborator даёт чтение и запись. Работа ведётся в своих ветках, релиз собирает исполнитель 1. |
| GitHub · облако | При подключении облачной среды выбирайте `Only select repositories → LIGI464/MTS`. Обе сессии используют только этот репозиторий. Для облачного режима с записью проверьте доступ на своей ветке. Если конкретная интеграция доступна только для чтения, человек переносит выданный патч в свою ветку и открывает PR. |
| SSH и VPS | Владелец VPS выдаёт именованный логин исполнителю 2, например `mts-deploy`, и добавляет предоставленный публичный ключ в `~/.ssh/authorized_keys` этой учётки. Сообщает IP или хост, порт SSH, логин и отпечаток хост-ключа. Системные действия и команды Docker выполняет владелец VPS или уже назначенный администратор. Обычная группа `docker` даёт полномочия уровня root. |
| Домен и HTTPS | Владелец домена создаёт запись `A` на отдельный поддомен, например `incidents.example.org`, с IPv4 VPS. `AAAA` добавляется при рабочем IPv6. На VPS владелец или администратор настраивает HTTPS в существующем прокси. Исполнитель 2 проверяет домен, сертификат и поток SSE. Порт приложения остаётся на loopback. |
| codex.sale и демо | Владелец аккаунта заполняет защищённый env на VPS · `CODEX_SALE_API_KEY`, `CODEX_SALE_MODEL` из каталога ключа, `MTS_AI_MODE=live`. Туда же записывается отдельный `MTS_OPERATOR_TOKEN`. Токен оператора используется при живом анализе и сбросе. Реальный шаблон `MTS_ITSM_URL_TEMPLATE` настраивается при наличии. |

Исполнитель 2 создаёт ключ у себя в PowerShell и отправляет владельцу сервера вывод последней команды. Если подходящий ключ уже есть, можно передать существующий файл `.pub`.

```powershell
New-Item -ItemType Directory -Force "$env:USERPROFILE\.ssh" | Out-Null
ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\mts_vps_ed25519"
Get-Content "$env:USERPROFILE\.ssh\mts_vps_ed25519.pub"
```

Закрытый SSH-ключ остаётся на ПК исполнителя. В Git и промтах используются имена переменных, а значения секретов вводятся на VPS.

## Что передать исполнителю 2

1. Ссылку на репозиторий и общий SHA после B00, затем релизный SHA после T51.
2. IP или SSH-хост, порт, имя учётки и подтверждённый отпечаток хост-ключа. Владелец VPS обозначает каталог приложения и кто выполняет системные команды.
3. Выбранный поддомен, информацию об имеющемся reverse proxy и выданную МТС выгрузку для загрузки на стенд. Уточнить, кто настраивает ключ модели и операторский токен. Передавать значения через защищённый канал или ввести их на VPS лично.
4. Договориться, кто проверяет первый и второй браузер. Согласованный результат · одна правка живого JSON, одна и та же новая ревизия и события в обоих браузерах.
