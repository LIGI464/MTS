# T52 · Команде goida-code · Проверь на двух ПК и отрепетируй защиту

Ты владелец итоговой репетиции. Прочитай [ТЗ](../TZ.md) и [контракт](../CONTRACT.md). Вход · релизный SHA T51 и адрес стенда T42 при наличии. Запиши результаты в `docs/mts/DEFENCE_LOG.md`. Выполняй проверки, доступные на каждом компьютере.

## Локально на двух ПК

1. На каждом ПК разверни один и тот же SHA. Выполни `npm ci` и `npm run build`. Зафиксируй ОС, браузер и SHA.
2. На ПК 1 импортируй выданный JSON перед запуском · `npm run data:load -- --file "<путь к character_problems.json>"`. Проверь, что загружены 44 записи и канонические статусы. Зафиксируй нулевую исходную критическую группу. На ПК 2 проверь независимый запуск на синтетическом наборе из чистого каталога. На каждом ПК запусти `npm start` и открой `http://127.0.0.1:8787/admin/incidents`. Оба варианта должны открывать четыре группы. Отдельно проверь `npm run dev` и mock-команду `npm run dev:web`, останавливая предыдущий запуск при конфликте порта. Для защиты используй режим API.
3. С включённым токеном раскрой «Служебное» ниже футера, проверь подтверждение и сброс. На основном экране действия сброса нет. Проверку некорректного JSON проводи на копии рабочего набора и восстанавливай удачным сохранением. Проверь случай временного отключения Wi-Fi в одной вкладке.

## Общий VPS

Открой один HTTPS-адрес с обоих ПК. Назначь одного оператора файла, чтобы два редактора не перезаписывали друг друга. Отдельно открой проводник или редактор JSON на VPS. Для реальной демонстрации редактируй файл руками или используй `demo:step`, который меняет эти же поля в этом файле.

| Порядок | Действие | Что видно на двух экранах |
|---|---|---|
| 1 | `npm run demo:step -- critical` | Активный высокий становится `4`. Сразу появляется карточка и одно оповещение |
| 2 | `npm run demo:step -- assign` | Тот же ID появляется у координаторов и остаётся критическим. Отображается второе смысловое оповещение |
| 3 | `npm run demo:step -- deadline` | У другого активного инцидента таймер показывает около 90 секунд. Проверяется подпись близкого срока или ожидаемое состояние по правилу SLA |
| 4 | Запусти анализ по второй активной карточке и посмотри источник | Выжимка, команда или «Команда не определена», риск с факторами. При живом ключе источник «codex.sale» |
| 5 | `npm run demo:step -- resolve` | Критический помечен решённым в уведомлении и доступен в истории |
| 6 | Сброс в нижней служебной секции | Исходный JSON восстановлен и оба браузера синхронно возвращаются к началу |

На VPS с Compose выполняй шаги внутри контейнера. Для первого шага команда выглядит так, остальные меняют последний аргумент.

```bash
docker compose --env-file "$MTS_VPS_ENV" -f deploy/compose.yaml exec -T dashboard npm run demo:step -- critical
```

Все шаги меняют файл в одном подключённом томе. Сервер продолжает работать.

- **0:00–0:35.** Что видит координатор. Покажи четыре группы и один SLA.
- **0:35–1:25.** Преврати инцидент в критический правкой JSON и назначь его координаторам. Покажи один ID в двух группах.
- **1:25–2:25.** Сократи срок другой карточке. Открой детали и анализ. Назови источник вывода и его факторы.
- **2:25–3:15.** Заверши первый инцидент через файл. Покажи тост и историю, затем переход в ITSM при настроенном шаблоне.
- **3:15–4:00.** Покажи второй экран с тем же актуальным состоянием. При необходимости продемонстрируй восстановление из скрытой секции.
